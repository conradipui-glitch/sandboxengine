# ADR 0005 — Declarative conditions и атомарные item transfers

Дата: 2026-09-06  
Статус: accepted

## Контекст

B02-02 доказал расчёт одного explicit action, но доступность действия ещё проверялась конкретной логикой resolver. Для переносимого движка нужен небольшой общий язык preconditions без `eval`, а уникальный предмет должен менять владельца/локацию тем же атомарным механизмом, что и ресурсы.

Критически важно различать два случая:

1. условие корректно и дало `false`;
2. условие ссылается на несуществующий ID или имеет неверную форму.

Если второй случай тихо превратить в `false`, ошибка определения квеста может остаться незамеченной. Аналогично, смешанный batch не должен списать ресурс, если следующая передача предмета оказалась невозможной.

## Решение

Вводится strict `Condition` v1.0 с первым ограниченным набором:

- `resource.atLeast`;
- `entity.at`;
- `item.heldBy`;
- `all`;
- `any`;
- `not`.

Это декларативные структуры данных. Произвольных JS expressions, `eval` и пользовательского кода в Condition нет.

`evaluateCondition` возвращает либо `{ ok: true, value }`, либо отдельный failure с кодом и broken reference. Композиции `all`/`any` проверяют все дочерние условия на целостность и не используют short-circuit, который мог бы скрыть битую ссылку.

`GameplayEffect` расширяется зарегистрированным `item.transfer`. Destination — ровно одна позиция: `location` или `holder`. Перед применением Core проверяет существование item и destination reference.

`tryApplyEffectBatch` создаёт trial-copy и ресурсов, и предметов. Результат возвращается только после успешного применения всего batch. При любой ошибке новый state не возвращается.

## Последствия

- T07 теперь проверяется смешанным batch resource + item.
- Condition evaluation остаётся чистой проверкой и не меняет state.
- Один предмет представлен одной `position`; отдельные независимые owner/location поля не вводятся.
- Отказ от short-circuit в первом evaluator — осознанный приоритет целостности authoring данных над микропроизводительностью.
- Новые condition/effect types добавляются только вместе со strict schema, Core-семантикой и тестами.
- Scheduler, social consent и runtime commit этим ADR не определяются.
