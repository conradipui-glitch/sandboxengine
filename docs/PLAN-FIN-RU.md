## Продукт

Платформа создания и прохождения интерактивных историй. Игрок принимает решения, история ветвится, сервер проверяет условия и применяет последствия. Авторы создают истории без программирования.

Две поверхности: закрытая веб-мастерская **Studio** на VPS (проекты, миссии, доска сюжета, редактор экранов, материалы, ИИ-помощник, проверка, публикация, командное обсуждение) и **игровой сайт** на Cloudflare (каталог и прохождение). **Engine** — серверные правила, данные, версии. **B13 Builder** — механизм изменения кода, не редактор сюжетов; автору публикации он не нужен.

Целевой пользовательский результат: вход в мастерскую → миссия из идеи → сцены на доске → выборы → оформление экранов → прохождение → «Опубликовать» → карточка на сайте → коллега открывает проект, понимает, комментирует и работает вместе. Без Git, JSON, SQL, SSH и ручного деплоя каждой истории.

Одна миссия ≠ одно место/ресурс/действие «Рисовать». Florence — старый пример, не универсальная структура. Alpha/Beta и «Приёмка VPS» — технические данные, не дизайн продукта; не удалять без разрешения, явно помечать.

## Неизменяемые правила данных

1. **MissionDraft** — listing, story, screens, defaults, ссылки на материалы; contentRevision/hash меняется при изменении видимого/исполняемого.
2. **BoardDocument** — рабочая раскладка; layout, presence и комментарии не меняют игровой hash и не инвалидируют проверенный релиз.
3. **MissionReleaseBundle** — неизменяемая версия: releaseId, точный MissionDraft pin, сюжет, экраны, listing, начальное состояние, manifest материалов с hashes, renderer compatibility. Семантику нельзя упростить до «ссылка на latest».
4. **PublicationRecord** — разрешённый публичный указатель на bundle в канале; preview и production различаются явно.
5. **GameSession** закреплена за одним bundle; правка draft, новая публикация и rollback не меняют начатую игру.
6. **Ассеты** неизменяемы по идентичности содержимого; старый bundle и открытая сессия сохраняют доступ к своим файлам; удаление из библиотеки ≠ физическое удаление используемого файла.
7. **Ход**: проверка входа/прав → условия → эффекты и переход → атомарная запись → идемпотентный результат.
8. **ИИ** предлагает данные или проверяемое намерение; не меняет состояние напрямую, не выдумывает asset IDs, не исполняет код из сюжета, не публикует без автора.
9. **Начальное состояние** новой публичной игры берётся из релиза, а не из присланного клиентом `initialWorld`.
10. **Доставка кода** и **публикация контента** — разные операции; новая история появляется на сайте без нового commit/build/deploy программы.

### FIN-01 — неизменяемый bundle и настоящий rollback (B02; M01/M06)
Места: `apps/server/src/control-server.ts`, `packages/control` (release/publication/mission persistence и миграции), потребители публичной сессии.
Долговременная привязка releaseId → точный bundle. Freeze/build фиксирует уже сохранённую и проверенную версию; publish и rollback только выбирают её. Существующий releaseId не меняет story/screens/listing/assets. Hash покрывает весь видимый и исполняемый контент без self-reference. Отсутствующие/битые материалы или несовместимый renderer блокируют готовность bundle с понятной ошибкой, а не хешируются как молчаливый null.
Переход со старых данных: не приписывать старому release текущий draft, если соответствие нельзя доказать; проверяемая миграция, резервная копия, отчёт о неразрешимых записях.
**Приёмка:** r1 с текстом/фоном A → игра A → draft v2 → новые игры всё ещё r1 → publish r2 с B → игра B → rollback r1 → игра C. A/C имеют r1, B имеет r2; тексты, экран, hash и материалы соответствуют версиям. После reopen БД соответствие сохраняется. Изменение ресурса/условия тоже меняет игровой контент. Client initialWorld не подменяет стартовые значения.

### FIN-02 — согласованная публикация, отказ и повтор (B03; M06)
Не лечить строкой `status: previous.status`. Предпочесть одну транзакцию, если данные в одной БД; иначе — долговременная операция pending/committed/recovery с reconciliation после crash. Кандидат не виден до commit; никакой best-effort компенсации поверх чужой новой версии.
Согласовать CAS/revision token, idempotency и публичный receipt. Таймаут после возможного commit → «проверяем результат»/operation lookup, а не уверенное «не опубликовано» с повторным независимым действием. Одинаковый ключ с другим запросом отклоняется; тот же запрос возвращает результат исходной операции.
**Приёмка:** unlisted + неверный CAS остаётся unlisted; чужая конкурентная публикация не затёрта; ошибка первого/второго шага, потерянный ответ и restart между стадиями не оставляют противоречивые pointer/catalog; две публикации одной base revision конфликтуют корректно; повтор не создаёт дубликат карточки. Проверять реальную SQLite, не только MemoryStore.

### FIN-03 — старые сессии сохраняют свои ассеты (B04; M03/M06)

**Приёмка:** r1 с фоном A и тремя PNG → открытая игра → r2 с набором B → unpublish. На пустом кэше старая игра получает A и прежние hashes, новая запрещена, приватный asset соседнего проекта недоступен. Проверить reload, MIME, прозрачность, отказ на повреждённый файл и сохранение после restart. Поправить старый тест, считавший исчезновение материалов после unpublish правильным.

### FIN-04 — согласованная доставка всех исполняемых компонентов (B01; R04)
Сначала собрать и проверить candidate локально. Manifest: Engine, Studio/Control, authored-runtime, Player/preview bundle, Worker — commit/image/file hashes и совместимость контрактов. «Хост checkout правильный» недостаточно: проверять фактически запущенные файлы/образы.

После доставки не должно остаться старого Control, пишущего старые данные в общую БД. Nginx направляет авторский и публичный пути в ожидаемые версии; на время несовместимой миграции старый writer не активен.
Резервная копия — проверяемая процедура восстановления SQLite/volumes с учётом WAL, не копирование горячего файла. Согласовать миграцию и rollback: старый бинарник может быть несовместим с новой схемой.
**Приёмка (в разрешённой среде):** assets Studio отдаются после входа; UI publish идёт в новый Control; runtime имеет healthcheck/restart policy; **ранее начатая** игра продолжается после контролируемого restart (новый create 201 не заменяет resume). Ссылки Studio/миссий и краткая инструкция — подготовить; статус «полная совместная версия» не ставить до FIN-12–14.

### FIN-12 — стикеры и комментарии (V07)
«Заметка»: текст, автор, положение на доске, спокойный различимый стиль; рабочий материал, не игровой узел и не часть release. Комментарий привязан к сцене/слою/полю либо к месту на доске; thread, reply, resolve/reopen, счётчик неразрешённых, автор и дата. Удалённый объект оставляет «Элемент удалён», обсуждение не теряется. Правила редактирования/удаления — по авторству и серверным правам; plain text или безопасный ограниченный Markdown; видны только обсуждения своего проекта; отозванный доступ прекращает чтение/запись; не только localStorage.
**Приёмка:** два аккаунта видят создание, ответ и resolve; после reload/restart всё сохранено; чужой проект закрыт; игровой hash не меняется; UI не перекрывает редактор и ИИ-composer.

### FIN-13 — настоящая совместная доска (V08)
Presence: реальные авторизованные участники, цвет/имя курсора, выделение, индикатор редактирования; координаты в системе доски, корректны при zoom/pan; «Показать, где работает» по клику на аватар, без принудительного follow.
Transport — по существующей инфраструктуре; authenticated WebSocket допустим, не обязателен. Проверять origin/session/project на соединении и изменения прав в процессе; heartbeat/TTL, ограничение частоты и coalescing; отключившийся исчезает. Движения курсора не писать в SQLite и worklog. Никаких seeded/fake cursors.
Совместное редактирование: изменения разных объектов не теряются; одновременное изменение одного поля имеет понятный conflict/lock/reconcile, не молчаливый last-write-wins; ревизии, undo и server authority сохраняются; набранный текст не исчезает; свой undo не отменяет чужое действие. CRDT во всё ядро не вводить без необходимости.
**Приёмка:** два реальных браузера/аккаунта на одной миссии, разные zoom; одновременные изменения разных сцен, конфликт одного текста, reconnect/offline, удаление выбранного объекта и отзыв доступа; итог совпадает после reload в обоих браузерах; стикеры и комментарии синхронизируются; старые игровые сессии не меняются от layout/presence.

### FIN-14 — окончательная приёмка и передача
Сокращённый regression индивидуального маршрута после collaboration-изменений, повтор матрицы ролей и критических recovery-сценариев. Согласованно доставить разрешённый командный релиз, записать версию каждого компонента; для production подготовить проверенный кандидат и точное действие на согласование.
Финальный пакет: проверенные адреса Studio и сайта без tickets/cookies/секретов; две показательные миссии авторским путём с разными материалами и ветвями; инструкция участнику (вход, новая миссия, доска, экраны, ИИ, тест, публикация, обсуждение); инструкция владельцу (приглашение/отзыв, роли, модели/лимиты, версии, backup/restore, rollback); manifest доставки, E-матрица, collaboration evidence, известные ограничения; техническая карта для следующего разработчика (репозитории, запуск, схемы/миграции, boundaries, тесты, путь изменения renderer/Engine без хардкода сюжета).
Финал достигнут, когда маршрут может повторить не только автор текущей сессии, но и приглашённый участник; правки/версии не ломают игры; ИИ работает живьём; совместная работа проверена; нет открытого критического нарушения контракта. Абсолютная невзламываемость не обещается; непроверенное обозначается как непроверенное.

## Понятность для обычного человека (UX-01…UX-08)

Пройти до закрытия FIN-05/06 и ещё раз после FIN-10.

1. **UX-01 фактический путь.** Войти обычным способом в hosted Studio, записать build identity, снять реальные экраны: первый вход → проекты → миссии проекта → создание миссии → пустая доска → выбранная сцена/выбор → экраны/материалы → проверка → публикация. Не обходить вход вызовом API. Для каждого шага: что видит человек, что должен понять, следующее действие, почему заметно, что при ошибке. Если вход не получен — отметить блокер, а не писать «проверил по исходникам».
2. **UX-02 базовые вопросы.** На каждом экране ясно: «Где я?», «Что создаю?», «Что дальше?», «Сохранилось ли?», «Как безопасно попробовать и вернуться?». Ориентир: новичок находит начало создания за 30 секунд и добавляет первую осмысленную сцену без технического руководства.
3. **UX-03 архитектура экранов.** Первый экран проекта — список миссий и одна основная кнопка «Новая миссия»; после открытия сразу полезная доска. Версии, portability, хеши, ресурсы и админформы — в настройках. Состояния project/mission/scene не выглядят и не называются одинаково.
4. **UX-04 предсказуемость.** Подсказка «Сцены — части истории. Соедините их решениями игрока», работающие «Добавить сцену»/«Создать с ИИ»; inspector соответствует выделению; имена кнопок описывают результат; иконка имеет tooltip и доступное имя; создание/удаление/публикация не срабатывают от просмотра.
5. **UX-05 механику не требовать до сюжета.** Ресурсы, условия и эффекты появляются в понятном конструкторе («Доступно, если…», «После выбора…», «Изменить запас…»); «Рисовать»/пигмент/Florence не обязательный старт; ошибка перехода ведёт к конкретной сцене/решению.
6. **UX-06 страх испортить работу.** Честное сохранение, безопасный playtest, undo, разница draft/published; «Проверить и сыграть» не публикует; «Опубликовать» показывает, что станет доступно; «Снять»/«Откатить» объясняют последствия; незавершённая генерация и закрытие панели не теряют введённое; отказ сервера не даёт ложного «Сохранено».
7. **UX-07 проверка на человеке.** Приглашённому: «Создай историю с двумя решениями, добавь фон, проверь и покажи ссылку» — без объяснения расположения кнопок. Записать места остановок, исправить основные препятствия, повторить. Автоматизированный проход не доказывает понятность; до реального участника это экспертная проверка.
8. **UX-08 внешний вид.** Ровная иерархия, читаемый русский текст, умеренная плотность, достаточная область доски, inspector без перекрытия, аккуратные пустые состояния, реальные превью. Проверить focus/клавиатуру, размер целей, ошибки, reduced-motion, узкий экран. Структурную путаницу не лечить фоном и перекраской кнопок.

## Как работать итерациями

Для каждой карточки: начало (SHA/diff, требование, точка входа, результат) → реализация (один связный срез; тест воспроизводит дефект до фикса или проверяет независимый контракт) → проверка (целевые suites и typecheck, браузер для UI, storage/restart для долговременности, реальный provider для AI-claim; у каждой команды exit code и смысл) → фиксация (commit, checklist, короткие HANDOFF/STATUS и worklog, следующий шаг). DONE не ставить там, где только unit PASS, а требование относится к VPS/браузеру.

Полный verify обоих репозиториев — на стабильных milestones и перед доставкой. CI success ≠ визуальная приёмка, скриншот ≠ persistence, healthcheck ≠ resume.

Параллельная работа в двух репозиториях — только с согласованным контрактом и независимыми checkout; не писать в рабочую копию другого агента и не запускать несколько миграций/деплоев одной БД параллельно. Конец фонового процесса ≠ готовая карточка.

Коммуникация: «Делаю FIN-…: результат …; проверено …; дальше …». Не задавать меню A/B/C по техническим деталям, уже определённым этим планом. Реальный блокер указывать конкретно.

Формат состояния карточки:

```text
FIN-XX / исходные M,E,B: …
Статус: LOCAL_PASS / HOSTED_PASS / PARTIAL / …
Что теперь может сделать пользователь: …
Code/renderer/deployment versions: …
Проверка: команда или пользовательский сценарий → фактический результат
Не проверено / блокер: …
Следующий шаг: …
```

## Что не входит в финал

Нативная desktop-программа, marketplace, оплата подписок, произвольный plugin store, собственный генератор изображений/видео, полная копия Figma, смена frontend framework, переписывание Core, новый VPS или перенос хостинга. Комментарии, стикеры и совместная доска **входят** в командный финал, но идут после рабочего индивидуального авторства.
