# FIN-01 — миграция дофиксовой базы (`feat/fin01-legacy-migr`, база 298c8ee)

## Что проверялось

До этой волны «старая» база моделировалась только `MemoryControlPublicationStore`:
durable-файла со старой схемой в тестах не было. Здесь воспроизведён **файл SQLite
со схемой до фикса** (релизы и публикации есть, пинов нет) и против него прогнан
фактический код сторов.

## Схема до/после

До (pre-pin, коммит `1886041^`): `control_projects`, `control_quests`,
`control_releases`, `control_release_pointers`, `control_release_events` (+индекс),
`control_release_idempotency`, `control_publication_records` (+индекс),
`control_publication_idempotency`.

После открытия текущих сторов добавляются ровно: `control_publication_release_pins`,
`control_publication_pin_idempotency`, `control_publication_operations` (+индекс).
`control_releases` не менялась ни в одной ревизии — весь разрыв миграции был на
стороне publication-стора. Строки не переписываются; версия схемы не поднималась,
обратная совместимость сохраняется (старый код на новой базе просто игнорирует
новые таблицы).

## Что происходит с неразрешимыми записями

`inspectLegacyReleaseMigration` классифицирует каждый релиз по уже существующим
доказательствам:

| вердикт | условие | доказательство |
| --- | --- | --- |
| `pinned` | есть пин | ревизия и манифест ассетов заморожены при публикации |
| `adoptable` | пин отсутствует, но запись публикации называет именно этот релиз | ревизия доказуема (записана при публикации), манифест — нет → adoption помечается `assetsVerified:false` |
| `unprovable` | ни пина, ни называющей записи | бандл неизвестен; **новейший draft не подставляется**, ничего не пишется, запись попадает в отчёт |

Записи публикаций дополнительно получают вердикт `reproducible` / `unresolvable`
(`LEGACY_RECORD_WITHOUT_REVISION` — колонки `draft_revision`/`draft_content_hash`
добавлены ALTER-ом с плейсхолдером; `MISSION_REVISION_UNAVAILABLE`;
`MISSION_REVISION_CHANGED`). Неразрешимые записи не переписываются: иначе публичный
контент менялся бы ради зелёной проверки.

## Процедура

```
npm run typecheck
node scripts/fin01-legacy-migration.mjs --db <control.sqlite> [--report <file.json>] [--no-backup]
```

1. резервная копия через SQLite online backup API (`backup()`, согласован с WAL) +
   `PRAGMA integrity_check` копии; существующая копия не перезаписывается;
2. открытие реальных сторов = миграция схемы (только недостающие таблицы/индексы);
3. JSON-отчёт: `schema.added`, вердикты по релизам и записям, сводка;
4. exit code `0` — чисто, `2` — есть записи, требующие решения оператора, `1` — сбой.

## Что не проверено / открытый дефект

* `resolveReleaseBundle` для релиза **без пина и без называющей записи** при
  `publish` подставляет новейшую authored-ревизию и пишет пин с
  `assetsVerified:true`. На реальной дофиксовой базе это приписывает старому
  релизу текущий draft (в файловой БД: `control_releases.draft_revision=0`, а пин —
  ревизия 3). Правка относится к `apps/server/src/control-server.ts`, который в этой
  волне править запрещено; инструмент миграции такой пин не пишет, а тест помечен
  `skip` с точной причиной. Пробел остаётся открытым.
* Схема базы-миссии не проверялась (миграция миссий — отдельная задача); в стенде
  она открывалась как есть.
* Конкурентный доступ/блокировки при миграции не проверялись (стенд однопроцессный).
* Восстановление из резервной копии не репетировалось в этой задаче (есть drill B12).
