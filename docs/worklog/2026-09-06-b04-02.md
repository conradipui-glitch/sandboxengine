# 2026-09-06 — B04-02 SQLite restart/fault recovery

## Цель

Доказать B04-01 operation/idempotency/fencing semantics через file-backed SQLite и реальные restart/fault cases, не добавляя HTTP.

## Реализовано

- `SQLiteRuntimeStorage` на built-in Node 24.19 `node:sqlite`.
- Минимальная versioned schema: runtime meta, sessions, operations, turns.
- Persistent operation counter и fencing counter.
- Short `BEGIN IMMEDIATE` transactions для claim/reacquire/renew/commit/finish.
- Canonical request hash, unique `(session,key)`, one active operation.
- Atomic session state + turn + public response + operation completion commit.
- Close/reopen durability.
- Injected ServiceClock отдельно от game clock.
- Bounded SQLite lock wait через adapter `timeout`, normalized `SQLiteStorageBusyError`.
- Test-only fault injector перед COMMIT.
- Shared RuntimeStorage semantic suite запускается на Memory и SQLite.

## Проверено

First functional PR #13 CI `34036777799` — success:

- contract 35/35;
- Core 55/55;
- storage 20/20;
- boundaries passed;
- docs check passed.

Ключевые regressions:

1. T10 SQLite durable — commit, потеря ответа, close/reopen, same key → persisted replay; revision/turn не удваиваются.
2. T11 SQLite durable — две независимые adapter instances на одном DB: только одна active operation.
3. T12 SQLite durable — writes до COMMIT откатываются при fault; после expiry/restart reacquire получает больший token; старый token отклоняется; current token commit проходит один раз.
4. `finishWithoutTurn` fault до COMMIT не освобождает owner и не сохраняет response.
5. Реальный competing SQLite write lock приводит к bounded busy error без partial operation.
6. Shared T10/T11/T12/invalid-candidate suite проходит одинаково на Memory и SQLite.

## Решение

ADR 0012. Built-in `node:sqlite` выбран вместо дополнительного native npm driver для pinned Node 24.19 runtime.
