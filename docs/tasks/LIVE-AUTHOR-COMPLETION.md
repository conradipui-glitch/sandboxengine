## 4. Границы ближайшего результата

Первый поддерживаемый пример — небольшая мастерская: локация, ресурс краски, одно действие покраски, изменение расхода/длительности по просьбе автора. Правила должны реально влиять на серверный результат.

Слова пользователя о других механиках нельзя молча переименовывать в покраску. Недоступная механика возвращается в `missingCapabilities` с понятным объяснением. Текущие ограничения интерфейса Player не превращать в глобальное ограничение Core или всех backend.

Сохраняются существующие preview, Apply, revision/hash checks, budgets, idempotency, immutable playtest, роли и server-authoritative state. Авторский помощник предлагает изменения контента; shell, git push и deploy ему здесь не предоставляются.

### L01. Локальные HTTP-границы

**Сделать:** после локальных проверок выполнить один ограниченный авторский цикл через выбранный пользователем/оператором провайдер и модель. Не искать ключи в чужих файлах и не пытаться прочитать GitHub secret. Использовать только явно предоставленный доступ.

Установить предел: два авторских запроса, до 8192 output tokens на запрос, до 60 секунд на запрос, без автоматических повторов. Это ограничение запросов, не обещание конкретной денежной стоимости; тариф и input tokens учитываются отдельно. Дополнительные попытки выполнять с явно записанной причиной и общим пределом.

Зафиксировать SHA, модель, дату, два пользовательских текста, результаты validate/Apply/Player, длительность и доступный usage. Ключ и сырые заголовки не сохранять. Оценивать отдельно JSON/contract и соответствие просьбе автора.

**Готово, когда:** настоящая модель создала связанные блоки и исправила именно существующий расход, а Player подтвердил правило. Если ключа нет, статус **UNVERIFIED: нет доступа к провайдеру**; локальную интеграцию можно передать отдельно, не заявляя live acceptance.

### L09. Завершение и передача

## 6. Что делать после сквозного маршрута

Эти задачи важны для исходного замысла, но не блокируют первый узкий работающий путь. Не смешивать их в один коммит с L01–L09.

| Следующий блок | Конкретный результат |
|---|---|
| Качество игрового intent | Разобрать неуспешные кейсы прежнего live eval, отделить ошибки каталога/парсера/модели, сравнить на одном корпусе с повторениями и измерением задержки. 12/12 валидного JSON не считать пониманием свободного действия |
| Баланс и лимиты | Подключить имеющийся quota adapter к UI; различать provider balance, rate limits и engine-local budget, учитывать timestamp/source/status. Не выводить остаток из числа использованных токенов; unsupported и null показывать явно |
| Codex subscription | Использовать существующий App Server adapter и документированный поддерживаемый login flow; отдельно подтвердить реальную сессию, logout/rotation и account isolation. Не обещать бесплатность или API-доступ из одной браузерной авторизации |
| Универсальный Player | Убрать ограничение одного paint через реальные action definitions и общий executor/UI; подтвердить как минимум второй тип механики без веток по id квеста |
| Визуальный авторинг | Связать существующие assets/presentation contracts с доступным выбором в Studio. Проверить картинки, текст, parallel/sequence/skip и fallback, сохранив gameplay state независимым от анимации |
| Постоянный сервер с AI | Отдельно спроектировать композицию провайдера для `npm start`, хранение секретов и authenticated deployment. Локальная форма Studio не является multi-user настройкой общего сервера |
| B13 Builder/GitHub/deploy | Отдельный режим/набор полномочий: изолированное рабочее дерево, diff, проверки, PR, затем конкретный deploy с журналом результата. Не давать author assistant произвольный shell ради генерации контента |

Точные endpoint/auth требования внешних систем при реализации сверять с их официальной документацией; не переносить старые предположения о тарифах и login в код.
