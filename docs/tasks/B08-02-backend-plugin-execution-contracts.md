# B08-02 — trusted backend plugin execution contracts

## Goal

Add the generic trusted in-process backend execution boundary required for B08 plugins without adding plugin-specific conditions to Core and without expanding plugin code into DB/HTTP/process authority.

Base: published B08-01 merge `375233479ab787a6215be7a1d6aab52ec9c47a74`, exact main CI `34105710910` — success.

Specification source: §12.2–12.4.

## Main invariant

**Plugin code may propose a bounded deterministic action/event plan; it may never return a mutated WorldState or commit gameplay directly. The host validates the plan and applies only canonical Core effects/time/scheduler semantics.**

## Do

### 1. Trusted executable registration separate from manifest

Add build-time registration objects outside the serializable manifest.

A registration may provide:

- one resolver per manifest-declared action type;
- optional handlers for manifest-declared scheduled event type IDs;
- deterministic argument validator callbacks supplied by trusted build code.

Requirements:

- registration IDs must exactly match the frozen B08-01 registry owner/plugin metadata;
- duplicate resolver/handler IDs fail before execution;
- registration object itself is not serialized into release/plugin manifest;
- no URL/source/eval/dynamic import surface.

### 2. Resolver input

Resolver receives only:

- a deeply frozen detached WorldState snapshot;
- already validated/frozen JSON args;
- deterministic simulation time (`elapsedSeconds`), never wall clock;
- bounded deterministic RNG capability supplied by the host;
- immutable action/plugin identity metadata.

Resolver does **not** receive:

- Runtime storage / database;
- HTTP request/response;
- process/env/filesystem/network;
- mutable WorldState;
- commit/transaction callbacks;
- unrestricted Core module object.

### 3. Resolver output

Introduce a bounded `PluginActionPlan` data contract with at minimum:

- action type;
- action status (`executed | partial | blocked`);
- requested/completed units or analogous bounded numeric counts;
- duration seconds;
- reason code/null;
- canonical `GameplayEffect[]` only in B08-02;
- optional canonical `SchedulerEvent[]` generated by the action;
- deterministic RNG provenance / final RNG state required when RNG was used.

The plan must not contain candidate state, state patch, SQL/HTTP data, callback, arbitrary executable object or presentation instructions.

### 4. Generic execution host

Add one generic host/adapter which:

1. resolves action type through the frozen plugin registry/registration map;
2. validates args before calling resolver;
3. supplies detached frozen state, simulation time and deterministic RNG;
4. catches resolver throws as explicit plugin failure;
5. validates returned plan shape, namespace/identity and hard bounds;
6. applies canonical effects via existing Core effect invariant gate;
7. applies duration using existing Core time/scheduler pipeline;
8. returns structured execution data + candidate state only after all validation succeeds.

A resolver must never receive the candidate state after effect application.

### 5. Scheduler handler boundary

Provide a generic adapter for manifest-declared plugin scheduled-event handlers.

Handler receives:

- canonical scheduler event;
- detached frozen state snapshot;
- deterministic scheduler context;
- optional deterministic RNG capability if explicitly needed by the registration contract.

It may return only bounded canonical `SchedulerEvent[]` in B08-02. Existing Core scheduler validates generated events and duplicate/past/event-count invariants.

No global `beforeAnything` / `afterAnything` hooks.

### 6. Custom effect rule

B08-01 manifest may declare namespaced custom effect IDs, but current canonical `WorldState` v1 has no `extensions[pluginId]` namespace.

Therefore B08-02 MUST NOT invent state patches or widen WorldState schema. A custom plugin effect in an execution result is unsupported/fail-closed until a separately versioned state-extension contract exists.

Resource changes remain canonical `resource.change`.

### 7. Determinism

- no `Math.random`, `Date.now`, process entropy or hidden mutable RNG in plugin host;
- RNG state/stream is explicit and replayable;
- same frozen state + args + registration + RNG seed/stream produces identical validated plan and candidate state;
- bounds prevent unbounded effects/events/duration/RNG draws.

## Tests

Minimum deterministic regressions:

1. valid trusted registration against B08-01 registry;
2. resolver ID absent from manifest/registry rejected;
3. duplicate resolver/handler rejected;
4. invalid args rejected before resolver invocation;
5. resolver sees detached deeply frozen state and frozen args;
6. mutation attempts do not change caller state;
7. deterministic RNG same seed/input gives identical result/provenance;
8. different seed can produce different plugin plan without hidden entropy;
9. resolver throw becomes explicit failure with no candidate state;
10. invalid/authority-widened plan rejected;
11. canonical resource effect goes through Core bounds and invalid effect batch fails atomically;
12. duration/time uses existing Core pipeline and no client/plugin arithmetic commits state directly;
13. generated scheduler event passes through existing scheduler validation;
14. custom/non-canonical effect fails closed;
15. no `if pluginId === ...` or equivalent plugin-specific branch is added to Core;
16. root `npm run verify` green.

## Functional acceptance

B08-02 is accepted when:

1. executable registration is trusted build-time code separate from data manifest;
2. resolver input is detached/read-only and deterministic;
3. resolver output is bounded data only;
4. Core remains generic and applies the same canonical effect/time invariants;
5. plugin action/scheduler lookup is registry-driven, never plugin-ID branching;
6. unsupported custom state effects fail closed;
7. semantic audit has zero unresolved BLOCKER.
