# ONE-DAY PRODUCT RESCUE

Это не новая архитектура движка. Это ограничение текущей работы до одного видимого результата.

## Что должно существовать в конце

Автор открывает Studio и делает один путь:

1. Пишет обычным русским языком идею новой кампании, которой раньше не было в коде.
2. ИИ отвечает понятным предложением: название, роль игрока, завязка, 6 игровых ситуаций/тактов, основные персонажи/ресурсы/правила и оформление карточки. До подтверждения ничего не публикуется.
3. Автор пишет корректировку обычным текстом или меняет поля в интерфейсе. ИИ/Studio обновляет ту же кампанию, а не создаёт дубликат.
4. Автор нажимает «Играть» и проходит созданную версию через существующий Player/игровую логику. Для rescue допускается только тот набор механик, который уже реально поддерживается кодом; неподдерживаемая механика должна быть названа человеку, а не имитирована.
5. Автор нажимает одну понятную кнопку «Опубликовать в preview».
6. После успешного preview-deploy на сайте «Переиграть историю» появляется карточка этой кампании с названием, тизером, ролью/периодом и оформлением. Карточка открывается и запускает именно опубликованную версию кампании.

Если любой из этих 6 пунктов не воспроизводится руками через интерфейс, результат НЕ готов, независимо от количества зелёных тестов.

## Источник истины

Работающая игра `conradipui-glitch/sandbox` — референс пользовательского поведения.

Нельзя заново проектировать Player или игровой цикл, если существующий `sandbox` уже умеет соответствующее поведение. Сначала переиспользовать его.

`sandboxengine` — склад уже построенных полезных деталей: AI authoring, draft/apply, validation, frozen playtest, Player, release/publish, assets, preview deployment. Не требуется использовать каждую деталь. Деталь подключается только если она непосредственно нужна одному из 6 пунктов выше.

## Что НЕ делать

- не создавать новый общий roadmap;
- не добавлять новые B/C/D-этапы;
- не строить plugin SDK, portability, роли, rollback, дополнительную изоляцию, универсальные абстракции или новые форматы ради будущего;
- не переписывать существующие работающие части ради «чистой архитектуры»;
- не делать production deploy в рамках rescue;
- не называть внутренний release pointer «публикацией на сайт»;
- не считать unit/type/contract tests доказательством пользовательского результата;
- не добавлять функцию без ответа на вопрос «какой из шести пунктов она делает возможным?».

## Минимальная техническая стратегия

### 1. Один пакет кампании

Нужен один переносимый объект данных, который уже существующая игра может прочитать. В нём только то, что видно игроку или реально нужно игре:

- id;
- title;
- period;
- role;
- hook/teaser;
- theme/card presentation;
- intro;
- шесть ситуаций/тактов;
- доступные подготовленные действия;
- поддерживаемые начальные ресурсы/правила;
- terminal/finale data.

Сначала представить существующую Florence в этом виде. Если после преобразования Florence перестала играть так же — формат неверен.

### 2. ИИ создаёт этот пакет, а не архитектуру

Author Assistant получает идею пользователя и текущий пакет кампании. Ответ пользователю сначала человекочитаемый. Структурные изменения применяются только после явного Apply/«Принять».

Новая кампания должна создаваться без ручного JSON и без ручного создания Project → Quest → Location → Resource перед разговором с ИИ. Эти технические сущности Studio создаёт сама при необходимости.

### 3. Studio — простой режим по умолчанию

Главный экран rescue:

- большое поле «Опишите кампанию» / чат с ИИ;
- слева структура: Вступление → Сцена 1…6 → Финал;
- по центру выбранная сцена;
- справа понятные свойства и оформление;
- сверху две главные кнопки: «Играть» и «Опубликовать в preview».

Существующие Versions/Access/Portability/Deletion и прочие инженерные панели не удалять из кода, но убрать из основного пути rescue (например, под «Дополнительно»), чтобы они не мешали автору.

### 4. Publish означает сайт

Существующий Control publish остаётся внутренней фиксацией версии.

Кнопка «Опубликовать в preview» считается успешной только после всей цепочки:

current authored version → frozen/release artifact → данные карточки/кампании доступны `sandbox` → deploy существующего preview workflow → HTTP smoke → URL preview.

Использовать уже существующий preview deployment adapter и workflow; не писать второй deployment subsystem.

## Приёмка руками

Использовать новую тестовую идею, которой нет в репозиториях. Например:

> «Короткая кампания: Константинополь, 1453. Игрок — управляющий небольшой генуэзской факторией. До штурма несколько часов; нужно решить, что вывезти, кому доверять и открывать ли ворота беженцам.»

Приёмка:

- [ ] вводим эту фразу в Studio;
- [ ] получаем осмысленный черновик кампании;
- [ ] просим: «сделай финал менее героическим и добавь дефицит лодок»;
- [ ] видим изменение существующего черновика;
- [ ] нажимаем «Играть» и совершаем минимум 2 реальных хода;
- [ ] нажимаем «Опубликовать в preview»;
- [ ] открываем preview сайта;
- [ ] видим новую карточку;
- [ ] открываем её;
- [ ] совершаем минимум 2 хода в опубликованной версии.

## Как отчитываться Antonio после каждого изменения

Только пять строк:

**Что сделали:** ...
**Что теперь может сделать Antonio/игрок:** ...
**Как проверили:** ...
**Чего эта проверка НЕ доказывает:** ...
**Следующий единственный шаг:** ...

Запрещён отчёт вида «T37/B14/CAS/sidecar green» без перевода в пользовательское поведение.

## Стоп-правило

Если для следующего шага предлагается новый subsystem или работа больше одного непосредственно видимого пользовательского результата — остановиться и сначала доказать, что без него один из 6 пунктов действительно невозможен.
